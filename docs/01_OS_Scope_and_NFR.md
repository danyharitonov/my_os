# my_os: границы системы и нефункциональные требования

## 1. Название и концепция

**my_os** — учебная операционная система с монолитным ядром, написанная на
Python 3.10+ и использующая SQLite как «диск». Название отражает индивидуальную
тему проекта — **квант времени**: основной акцент сделан на подсистеме
управления процессами и планировщике Round Robin с приоритетами. Файловая
система, память и учётные записи реализованы в объёме, достаточном для
демонстрации полного пути «команда → системный вызов → ядро → подсистема → БД».

Принцип проекта: пользовательский код (оболочка) никогда не обращается к базе
напрямую — только через системные вызовы, каждый из которых журналируется.

## 2. Границы системы

### 2.1. Что входит в my_os

| № | Подсистема | Что реализуется |
|---|------------|-----------------|
| 1 | Процессы и планировщик | создание (`sys_exec`), список (`sys_ps`), завершение (`sys_kill`), очередь готовых процессов, квант времени, приоритеты 0–3, состояния new → ready → running → waiting → terminated |
| 2 | Память | учёт выделенной памяти по процессам в КБ, общий лимит, отказ при превышении |
| 3 | Файловая система | плоское пространство путей вида `/home/<user>/<file>` в таблице `files`: создание, чтение, удаление, список |
| 4 | Пользователи и права | вход/выход, роли `admin` и `user`, хэши SHA-256, проверка владельца |
| 5 | Журнал | запись каждого системного вызова в `syscalls_log` |
| 6 | Оболочка | интерактивный цикл команд, приглашение `пользователь@my_os` |

### 2.2. Что не входит (и почему)

| Функция | Обоснование исключения |
|---------|------------------------|
| Работа с реальным оборудованием, прерывания | требует ассемблера и привилегированного режима процессора; Python исполняется в пространстве пользователя хост-ОС |
| Драйверы устройств | заменяются заглушками (таймер планировщика — счётчик тиков) — реальные драйверы не помещаются в 6 занятий |
| Настоящая виртуальная память, страничная трансляция | нет доступа к MMU; память моделируется числом килобайт в таблице `processes` |
| Иерархические каталоги и права rwx | для темы «планирование» достаточно владельца файла; иерархия удвоила бы объём ФС |
| Сеть, сетевые протоколы | не связаны с темой, требуют отдельного стека |
| Графический интерфейс | демонстрация ведётся в терминале VS Code |
| Многопоточность и истинная параллельность | планировщик моделирует разделение времени на одном «процессоре» |
| Службы каталогов (LDAP, AD) | пользователи хранятся локально в SQLite |

## 3. Роли и сценарии использования

**Роли:** гость (`guest`, до входа: только help/echo/whoami/login), пользователь
(`user`: свои файлы и процессы), администратор (`admin`: всё, включая чужие
процессы, журнал и выключение), система (`system`: планировщик, создаётся ядром).

| № | Сценарий | Действующее лицо | Системные вызовы | Модули |
|---|----------|------------------|------------------|--------|
| С1 | Вход в систему | гость | `sys_login` | shell → syscalls → kernel → auth → db |
| С2 | Кто я | любой | `sys_whoami` | shell → syscalls → kernel |
| С3 | Создание файла | user | `sys_create_file` | shell → syscalls → kernel → auth(права) → fs → db |
| С4 | Чтение файла | user | `sys_read_file` | shell → syscalls → kernel → fs → db |
| С5 | Список файлов | user | `sys_list_files` | shell → syscalls → kernel → fs → db |
| С6 | Запуск процесса с приоритетом | user | `sys_exec`, `sys_mem_alloc` | shell → syscalls → kernel → memory → scheduler → db |
| С7 | Один такт планировщика | system | `sys_tick` | syscalls → kernel → scheduler → db |
| С8 | Список процессов | user/admin | `sys_ps` | shell → syscalls → kernel → scheduler → db |
| С9 | Завершение процесса | владелец/admin | `sys_kill` | shell → syscalls → kernel → auth → scheduler → memory → db |
| С10 | Журнал вызовов | admin | `sys_logs` | shell → syscalls → kernel → db |
| С11 | Выключение | admin | `sys_ps`, `sys_kill`, `sys_shutdown` | shell → syscalls → kernel → все подсистемы |

Пример детализации С6: пользователь вводит `run compiler 3 512`; оболочка
вызывает `sys_exec("compiler", priority=3, memory_kb=512)`; ядро проверяет вход
пользователя, просит память у `memory` (при превышении лимита — отказ и запись
`denied` в журнал), создаёт запись в `processes` в состоянии `ready` и ставит
PID в очередь планировщика соответствующего приоритета.

## 4. Нефункциональные требования

| Код | Категория | Требование | Метрика / способ проверки |
|-----|-----------|------------|----------------------------|
| NFR-P1 | Производительность | время обработки одного системного вызова | ≤ 50 мс, `time.perf_counter()` в тесте `test_nfr` |
| NFR-P2 | Производительность | одновременно активных процессов | ≥ 10, тест создаёт 10 процессов |
| NFR-P3 | Производительность (тема) | один такт планировщика (`sys_tick`) при 10 процессах | ≤ 20 мс |
| NFR-P4 | Производительность (тема) | время ожидания процесса в очереди | не более (N−1)·квант тиков для процессов одного приоритета |
| NFR-R1 | Надёжность | исключение внутри вызова не роняет ядро | вызов возвращает ошибку, в журнале статус `error` |
| NFR-R2 | Надёжность | превышение лимита памяти | `sys_mem_alloc`/`sys_exec` возвращают −1, процесс не создаётся |
| NFR-R3 | Надёжность (тема) | отсутствие «голодания» | процесс низкого приоритета получает квант не реже 1 раза за 8 тиков (aging) |
| NFR-S1 | Безопасность | пароли только как SHA-256 | в `users.pwd_hash` 64 hex-символа, тест |
| NFR-S2 | Безопасность | user не может удалить/убить чужое | тест «student kill pid root» → False |
| NFR-S3 | Безопасность | журнал каждого вызова: имя, аргументы, пользователь, статус | число строк лога растёт на 1 за вызов |
| NFR-S4 | Безопасность | пароли не пишутся в журнал | в `args` вместо пароля `***` |
| NFR-M1 | Поддерживаемость | модуль ≤ 300 строк, одна ответственность | `wc -l src/*.py` |
| NFR-M2 | Поддерживаемость | вызовы только «сверху вниз» по диаграмме | проверка импортов |
| NFR-M3 | Поддерживаемость | покрытие тестами всех вызовов | `python -m unittest` |
| NFR-E1 | Ресурсоёмкость | только стандартная библиотека Python 3.10+ | нет `requirements.txt` |
| NFR-E2 | Ресурсоёмкость | лимит «памяти» ОС | 4096 КБ на все процессы (`config.MEMORY_LIMIT_KB`) |
| NFR-E3 | Ресурсоёмкость | размер `os.sqlite` после демонстрации | < 1 МБ |

## 5. Анализ рисков

| № | Риск | Вероятность | Стратегия минимизации |
|---|------|-------------|------------------------|
| R1 | Не успеть всё реализовать | высокая | порядок: БД → вызовы → планировщик → ФС → оболочка; остальное — заглушки |
| R2 | Блокировки SQLite | средняя | одно соединение `db.get_connection()` на процесс, `commit` после каждой записи |
| R3 | Трудная отладка вызовов | средняя | сквозной журнал `syscalls_log` с аргументами и статусом |
| R4 | Забытая обработка ошибок | средняя | единый декоратор журнала ловит исключения во всех вызовах |
| R5 | Потеря целостной картины | низкая | документы `docs/01`, `docs/02`, диаграмма компонентов |
| R6 (тема) | Голодание низкоприоритетных процессов | средняя | старение (aging): +1 к приоритету за каждые 4 пропущенных такта |
| R7 (тема) | Расхождение очереди в памяти и таблицы `processes` | средняя | состояние процесса пишется в БД при каждом переходе; при старте очередь восстанавливается из БД |
| R8 | Пароли в открытом виде в истории Git | низкая | `*.sqlite` в `.gitignore`, в коде только хэширование |

## 6. Прототип (день 1)

| Модуль | Назначение | Как проверить |
|--------|------------|---------------|
| `src/config.py` | пути и константы | — |
| `src/db.py` | соединение и создание 4 таблиц | `python src/db.py` → появляется `db/os.sqlite` |
| `src/syscalls.py` | `log_syscall`, `sys_echo`, `sys_get_users` | `python -m src.syscalls` |
| `src/shell.py` | баннер, команды help/echo/users/exit | `python -m src.shell` |

После команд `echo` и `users` в таблице `syscalls_log` появляются строки
`sys_echo` и `sys_get_users` (проверяется в SQLite Viewer).

## 7. Словарь терминов

| Термин | Определение |
|--------|-------------|
| Ядро | центральная часть ОС, выполняющая привилегированные операции по запросам программ |
| Kernel Space | защищённое пространство, где работает ядро |
| User Space | пространство прикладных программ и оболочки |
| Системный вызов | формальный интерфейс запроса услуги ядра из пространства пользователя |
| Процесс | программа в момент выполнения со своим состоянием и ресурсами |
| PID | уникальный номер процесса |
| Планировщик | модуль, выбирающий процесс, который получит процессор |
| Квант времени | максимальный отрезок, в течение которого процесс выполняется до вытеснения |
| Round Robin | циклическое планирование: процессы по очереди получают по кванту |
| Приоритет | число, определяющее очерёдность выбора процесса планировщиком |
| Старение (aging) | постепенное повышение приоритета долго ждущего процесса против голодания |
| Контекст | сохранённое состояние процесса, восстанавливаемое при возобновлении |
| Дескриптор файла | идентификатор открытого файла для последующих операций |
| Аутентификация | проверка подлинности пользователя (логин + пароль) |
| Авторизация | проверка права пользователя на действие |
| Хэш-функция | необратимое преобразование данных в строку фиксированной длины (SHA-256) |
| Монолитное ядро | архитектура, где все подсистемы ядра работают в одном адресном пространстве |
